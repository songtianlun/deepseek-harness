# Agent Note: 由路由自身端点扩充目录路由的模型

Status: implemented

[English](2026-09-17-catalog-route-endpoint-widening.md) | 中文
## 问题

模型发现对已安装目录覆盖的路由只由该目录作答。目录是在 pi-ai 发布时生成的，而提供方会持续向一个已经存在的路由添加模型，因此 Models 页面给出的模型少于该路由实际可服务的模型，也没有任何办法找出其余的模型。用户也无法采纳发现结果没有报告的模型：profile 的 `models` 列表会整体替换该路由的目录，所以要新增一个模型，就得手工重述其余每一个模型及其容量。

这个缺口并非假设。pi-ai 0.85.1 为 `opencode-go` 提供 27 个模型；`GET https://opencode.ai/zen/go/v1/models` 在 2026-09-17 列出了 38 个，缺少 `minimax-m2.5`、`kimi-k2.5`、`glm-5`、`deepseek-flash`、`deepseek-v4.1-flash`、`qwen3.5-plus`、`mimo-v2-pro`、`mimo-v2-omni`、`union-alpha`、`hy3-preview` 与 `grok-4.5`。同一端点在早一小时还列出 39 个，因此它的任何快照也无法保持最新。

## 决策

已安装目录覆盖的路由先由该目录作答，再由该路由解析出的端点加以扩充。目录保留它描述的每一个 id，因为其条目带有列表端点不会披露的上下文窗口与输出上限；端点则补充它正在服务、而目录尚未跟上的 id，按端点顺序排列。

扩充是尽力而为的：凭据无法解析、端点拒绝或无法访问、应答不是模型列表、本构建读不了该协议的列表，或该路由没有唯一端点，都会让目录回答保持不变，因为该回答本身已经完整。调用方取消不属于这些故障，仍然会让操作失败。

### 列表端点从何而来

指名某个路由的请求可以省略端点与协议，正如 Models 页面在发送已存 profile 的草稿时那样；Host 会从该路由补上它们，与它此前提供的已存凭据和部署标头并列。[`modelEndpoints`](../../../../packages/llm/llm-pi-ai/src/catalog.ts) 会报告该路由的模型各自由哪种线协议从哪个端点服务——端点按协议区分，是因为像 `opencode-go` 这类由 pi-ai 按模型存储地址的路由没有唯一端点——被询问的协议则是 profile 明确写出的那个，否则是该路由具备的 [`LISTING_PROTOCOLS`](../../../../packages/llm/llm-pi-ai/src/discovery.ts) 中的第一个。某个协议下的模型各自使用不同端点时（如 Bedrock 的区域端点），该协议即从该映射中缺席，而没有任何可用端点的路由则停留在目录回答。

## 考虑过的替代方案

**在发现逻辑内询问 pi-ai 的提供方级端点。** 许多提供方在 provider 自身上声明了 `baseUrl`，因此适配器无需任何 Host 输入就能回答该问题，也能把端点挡在发现请求之外。它失败的原因是：最需要扩充的路由恰恰没有这样的端点——`opencode-go` 与 `opencode` 把地址存在每个模型上，而目录中尚无 profile 的条目没有别的东西可解析。

**无论是否已配置，都扩充每一条目录路由。** 这样表述更简单，也能在添加提供方的同一次查看中完成刷新。它失败的原因是：没有 profile 的路由没有凭据可用，于是该动作会向每个已安装提供方的端点发送未认证请求，并把由此产生的拒绝报告成「提供方不提供任何模型」。

**在本仓库内置缺失的模型，或升级 pi-ai。** 两者都能修好今天观察到的列表，且不需要网络请求。它失败的原因是：0.85.1 已是最新版本，其目录仍落后于端点；而手工维护的叠加层重复了 pi-ai 的职责，还会按 pi-ai 自己的节奏过期。

**由端点而非目录作答。** 提供方是它当下所服务模型的权威，其回答不会过期。它在两点上失败：列表常常按账号限定，因此有权子集反而会隐藏该路由可服务的模型；而列表不披露任何容量，采纳的每一行都需要手工填写。

**让 `models` 扩充目录而不是替换它。** 这是上述难点的另一半。它失败的原因是：替换语义已有文档与测试，也是收窄路由的方式；而且它仍要用户手工知道每一个新 id——发现这些 id 才是缺失的那一步。

## 后果

Models 页面现在可以从服务该路由的提供方刷新一条已配置的目录路由：新发布的模型作为候选出现，采纳后写入 profile 显式的 `models` 列表，此后该列表即替换目录。代价是：该动作此前不发任何网络请求，现在会发一次；而扩充失败只表现为什么都没多出来，因为 seam 的应答携带的是候选而非警告。端点未披露的容量仍会落到该路由的 `defaultContextWindow` 与 `defaultMaxTokens`，因此采纳的模型若比目录更新，通常还需要填入真实数值。

## 测试

`packages/llm/llm-pi-ai/tests/discovery.spec.ts` 覆盖扩充后的回答、端点故障时目录回答依然成立、不可读的协议、无法解析的凭据，以及取消仍使操作失败，并回放 `opencode-go` 于 2026-09-17 发布的应答，证明 pi-ai 0.85.1 缺少的模型会作为候选到达。`packages/llm/llm-pi-ai/tests/catalog.spec.ts` 覆盖每种协议解析出的端点，包括同一协议下模型端点不一致的情况。`packages/llm/llm-pi-ai/tests/loader-composition.spec.ts` 启动真实 Loader 组合，证明在设置中重定向的目录路由会经 Host 提供的端点、携带其已存凭据完成扩充。
